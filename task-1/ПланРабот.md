# Разбор Задания 1: суть и архитектурные концепции

В **Задании 1** перед нами стоят две взаимосвязанные подзадачи:

#### Подзадача 1. Архитектура управления учетными данными (диаграмма C4 в draw.io)

Бизнес BionicPRO выходит на международный рынок и работает с персональными и медицинскими данными. Согласно законам разных стран (например, 152-ФЗ в РФ, GDPR в ЕС, HIPAA в США), персональные и медицинские данные граждан должны храниться локально в стране их юрисдикции.

Чтобы решить эту задачу, в материалах спринта рассматриваются два ключевых паттерна:

1. **Федерация удостоверений (Federated Identity / User Federation)**:

* В каждой стране разворачивается или подключается свой доверенный **Identity Provider (IdP)** (локальный Keycloak), который хранит профили и ПДн граждан этой страны на локальных серверах.

* Центральный Keycloak компании BionicPRO выступает брокером (Identity Broker): он не хранит сами учетные записи иностранцев, а перенаправляет пользователя на IdP его страны по протоколам SAML 2.0 или OpenID Connect (OIDC). В ответ центральный сервис получает только валидированное утверждение (assertion / id_token) и маппит внешние роли на внутренние роли системы (prothetic_user).


2. **Безопасная схема работы с токенами (BFF / исключение токенов на фронтенде)**:
* ТЗ требует: *«исключить передачу фронтенду токенов, которые были получены от IdP»*.
* Когда одностраничное приложение (SPA) хранит access/refresh токены в браузере (`localStorage`), оно уязвимо к XSS-атакам и краже данных.

* Архитектурный паттерн для решения этой проблемы — **Backend for Frontend (BFF)** или API Gateway с управлением сессиями: токены хранятся внутри защищенного бэкенда, а фронтенд общается с ним через зашифрованные защищенные сессионные куки (`HttpOnly`, `SameSite=Strict`, `Secure`). Токены IdP браузеру напрямую не отдаются.


#### Подзадача 2. Защита мобильного/SPA приложения: замена Code Grant на PKCE

* **В чем была уязвимость?** В стандартном *Authorization Code Grant* клиент получает временный код авторизации через редирект в браузере/приложении. Если злоумышленник перехватил этот код (например, через подмену схемы URI на устройстве или перехват трафика), он мог отправить его на авторизационный сервер и получить токен.

* **Как спасает PKCE (Proof Key for Code Exchange)?** Клиент генерирует случайный секрет `code_verifier` и его хеш `code_challenge = SHA256(code_verifier)`. Серверу при старте отдается только хеш. При обмене кода на токен клиент отправляет сам `code_verifier`. Даже перехватив код, злоумышленник не знает `code_verifier` и не сможет забрать токен.

### Анализ требований Задачи 1

1. **Унификация доступа через внешний источник в стране представительства (без нарушения законов о локализации ПДн и медданных):**
* У компании появляются зарубежные клиенты/пациенты. Законодательство (GDPR, HIPAA, 152-ФЗ) запрещает бесконтрольную передачу медицинских и персональных данных за пределы юрисдикции.


* **Архитектурный ответ из курса:** использование **Federated Identity (User Federation)**.


* В стране присутствия размещается **внешний поставщик удостоверений (Local / Regional IdP)** (например, локальный Keycloak или Active Directory / OpenLDAP), в котором хранятся профили и персональные данные граждан этой страны.


* Центральный Keycloak компании BionicPRO в РФ выступает в роли **Identity Broker (брокера федерации)**: он перенаправляет пользователя на IdP его страны по протоколам SAML 2.0 или OIDC, проверяет валидность токена/assertion и маппит внешние роли во внутренние роли BionicPRO (например, `prothetic_user`), не перенося сами исходные базы ПДн в РФ.






2. **Безопасная схема работы с токенами, исключающая их передачу на фронтенд:**
* Если SPA-приложение или браузер хранят `access_token` и `refresh_token` в `localStorage` / памяти, они подвержены атакам перехвата и утечкам (что и привело к взлому BionicPRO).


* **Архитектурный ответ из курса:**
* Токены от IdP должен забирать и хранить защищенный серверный слой.


* В архитектуру вводится паттерн **BFF (Backend for Frontend) / API Gateway** (в терминах C4 — контейнер шлюза/прокси между фронтендом и бэкендом).


* Фронтенд общается с BFF через защищенные сессионные куки (`HttpOnly`, `SameSite=Strict`, `Secure`), а сам BFF при запросах к API подставляет `Bearer <access_token>`. Таким образом, фронтенд токенов IdP напрямую не видит.






3. **Поддержка аутентификации через различные внешние службы (OIDC, SAML, Kerberos):**
* Брокер Keycloak берет на себя адаптацию разных внешних протоколов (SAML для корпоративных систем, OIDC для облачных провайдеров) к единому формату авторизации внутри контура BionicPRO.

### Логика потока To-Be на диаграмме C4

```
[Пользователь / Пилот]
       │ (1. Вход в систему)
       ▼
[Приложение BionicPRO (Фронтенд)] ──(2. Запрос на авторизацию)──► [BFF / API Gateway]
                                                                        │
                                                                 (3. Перенаправление)
                                                                        ▼
                                                             [Центральный Keycloak (Broker)]
                                                                        │
                                                              (4. OIDC / SAML Federation)
                                                                        ▼
                                                             [Внешний локальный IdP (Страна филиала)]
                                                                        │
                                                              (5. Локальная база ПДн)

```

1. Пользователь запрашивает вход в приложение.


2. Запрос идет на BFF-слой, который направляет браузер в Центральный Keycloak компании BionicPRO.


3. Keycloak перенаправляет запрос на соответствующий локальный IdP в стране пользователя (по протоколу SAML 2.0 / OIDC).


4. Локальный IdP проверяет учетные данные в локальной базе страны и возвращает подписанный assertion/token брокеру.


5. Keycloak сопоставляет атрибуты пользователя с внутренней ролью (`prothetic_user`) и возвращает токен BFF-шлюзу.


6. BFF выпускает защищенную `HttpOnly` сессию для фронтенда — фронтенд никогда не держит в себе access/refresh токены провайдера.
